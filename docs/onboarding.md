# Profile, objective and optional nutrition setup

Authenticated Basic and Clerk access reads `GET /api/v1/auth/me`. The backend returns `onboarding.profile_complete`, `objective_selected` and `required`; `GET /api/v1/me` remains compatible. Returning accounts with incomplete profiles or no objective enter setup again. Client routing never substitutes for backend ownership checks.

During onboarding, complete three guided steps: name and optional photo, personal information (age and measurements), then confirmation. Back preserves your entries; each step validates its own inputs. The photo uses pencil and delete controls; selections and removals stay local until the final confirmation, with no separate photo-save action. Profile pictures are selected from your image library and uploaded as multipart files to private Azure Blob Storage. No pasted image URL is required. The profile requires an explicit Metric or Imperial choice. Metric displays kg and cm; Imperial displays lb, feet and inches. Measurements display two decimal places (feet and age are whole numbers). Switching systems converts the current entries. Height is always stored in cm with two decimal places and weight in canonical kg with six decimal places; conversions use exactly 2.54 cm per inch and 0.45359237 kg per lb. Reopening or switching without editing preserves stored precision. No system is silently selected. The four distinct objectives are Build muscle, Lose fat, Gain weight and Maintain weight. Profile and objective remain editable from the dedicated Profile tab; Home provides shortcuts. Editing an existing profile uses a compact single-page form with all fields visible, a smaller picture control, and Save in the header. It has no setup steps or confirmation screen. Picture changes remain local until Save; Back cancels the unsaved draft.

Saving the profile and objective completes onboarding. Nutrition setup is optional and available from Profile, Home or Nutrition. A compact editor combines daily kcal, three macro rows, a calorie-budget summary and Save. Choose Percentages or Grams: the editable values use that unit, and each row shows its live equivalent in the other unit. Sliders and numeric inputs stay synchronized. Inputs accept up to two decimals using a decimal point or comma. There are no preselected calories or macro values. Tap the info icon beside a macro for its kcal per gram; the tooltip points to its source and closes when you tap outside.

Macro values are independent: editing one does not redistribute the others. Percentage mode requires a total of exactly 100.00% to save. Gram mode permits amounts below the calorie budget. Both modes display the required macro calories, percentage of the daily budget and remaining calories or an explicit out-of-budget warning. Save is disabled while over budget. For example, a 2,000 kcal budget with 60% carbohydrate, 30% protein and 30% fat requires 2,400 kcal (120%), so the editor shows a 400 kcal excess and requires adjustment. This is arithmetic, not a nutritional recommendation.

Conversion uses 4 kcal/g for carbohydrate/protein and 9 kcal/g for fat. Integer-hundredths arithmetic rounds grams half up to 0.01 g and displayed percentages to 0.01%. A 2,000 kcal fixture at 40/30/30 produces 200 g carbohydrate, 150 g protein and 66.67 g fat. Gram-mode budget comparison tolerates up to 0.09 kcal to account for the maximum 0.085 kcal introduced by rounding three gram values to 0.01 g; this prevents a valid percentage split from becoming unsavable when switching units.

The API continues to persist calories and grams. Opening or changing modes never saves or normalizes a target. Switching modes without edits restores the exact original draft, including legacy gram values and zero macros, avoiding repeated conversion drift. Editing a value converts the next mode from the changed draft. Existing targets below budget remain directly editable in Grams; in Percentages their shares must total 100% before saving. Failed saves retain entered values and allow retry; changing accounts resets private drafts and returns to Percentages. Each explicit save records the selected objective context. Scientific suggestions remain a separate later increment.

The slider uses the Expo-compatible `@react-native-community/slider` dependency. Rebuild native development clients after installing this dependency.

A missing target shows an absent amount (`—`) and permits food logging and daily totals. Only the target API's 404 means absence; network/server failures remain retryable errors. Meals, body measurements, chosen targets and suggestions are separate data.

Physical targets, milestones and weekly-session targets are not implemented by this flow. Scientific suggestions are tracked in [the high-priority Sprint 2 follow-up](https://github.com/kinetix-app/app/issues/74), under [Kinetix-010](https://github.com/kinetix-app/app/issues/13). Formula choice and additional-input requirements await that decision; no extra sensitive fields are inferred.

## Profile photo storage and device setup

Profile photos are optional. JPEG, PNG and WebP uploads are limited to 5 MiB; the backend validates actual image contents and strips metadata while normalizing the stored image to JPEG. Selection does not contact storage; the final confirmation sends the staged photo change. Upload failure preserves the previous saved photo and offers retry; removing a photo does not clear the other profile fields.

The app sends multipart field `file` to `POST /api/v1/me/profile/picture` using its shared authenticated client. `GET` at the same path reads the signed-in account's private image; `DELETE` removes it. The app fetches the protected image with its authorization header and uses an in-memory preview, rather than putting session credentials in image URLs. Existing HTTPS image references remain compatible.

Install locked dependencies and rebuild native development clients after adding `expo-image-picker`. The picker uses the image library; camera capture is outside this increment. Browser verification does not establish native picker permissions or gallery behavior.
